# Outage 2026-08-29: two independent failures, neither self-healing

Found during a routine "is everything online" check. Two separate faults had
been running silently - one for 20 hours, one for 41 hours. Nothing alerted.

---

## Fault 1: an NVIDIA driver update took the NVR down

### Timeline

```
2026-08-27 22:0x   cam4_hallway stops recording   (fault 2, unrelated, see below)
2026-08-28 22:01:09  Windows installs nvlddmkm     (NVIDIA driver -> 616.56)
2026-08-28 22:01:58  Frigate begins shutdown       49 seconds later
2026-08-29 18:25     discovered - 20 hours of no recording on all six cameras
```

### What it looked like

Frigate had exited **143** with a completely clean shutdown - every camera
process stopped in order, `peewee` closed its writer, s6 stopped each service
with code 0. It reads exactly like somebody typed `docker stop frigate`.

`restart: unless-stopped` had not brought it back, which reinforced the wrong
story: that policy deliberately does not restart a container that was stopped
on purpose. Shell history was empty. No `docker stop` was ever run.

### What it actually was

The Windows NVIDIA driver updated underneath a **running** WSL2 VM.

`/usr/lib/wsl/lib` is bind-mounted from the Windows host when the VM boots.
It does not re-mount. So after the update the VM was left holding the old
userspace driver while Windows had moved on:

```
Windows KMD          616.56      (new)
WSL /usr/lib/wsl/lib 610.57.01   (stale, from before the update)
```

The symptom is misleading in both directions:

```
$ ls -l /dev/dxg
crw-rw-rw- 1 root root 10, 258      <- device present, looks fine

$ nvidia-smi
Failed to initialize NVML: GPU access blocked by the operating system

$ docker compose up -d
nvidia-container-cli: initialization error:
  WSL environment detected but no adapters were found
```

"No adapters were found" on a machine with a working RTX 4080 sends you looking
at the GPU. The GPU was never the problem. The mount was.

### Fix

```
wsl --shutdown          # remounts /usr/lib/wsl/lib from the current driver
```

Then bring the stack back up. Verified after:

```
NVIDIA-SMI 615.65.06   KMD Version: 616.56   CUDA UMD Version: 13.4
NVIDIA GeForce RTX 4080 SUPER    detector inference ~4-16 ms
```

### The part that matters

**This will happen again on every NVIDIA driver update.** Nothing in the stack
recovers from it:

- Docker's `restart: unless-stopped` cannot help - the container cannot *start*,
  the prestart hook fails before the process exists.
- The WSL keepalive boot task keeps the VM alive, which is precisely what
  preserves the stale mount. It makes this failure mode *more* likely, not less.
- The failure is silent. No notification, no alert, no entry anywhere you would
  routinely look.

A `wsl --shutdown` is required, and something has to notice that it is required.

## Fault 2: cam4 answered HTTP for 41 hours while serving no video

This is the gap that was already known and written down as a gap. It happened.

`cam4_hallway` last recorded at **2026-08-27 22:00**. It was still, at the time
of discovery:

- responding to HTTP 200 on `/cgi-bin/status.json`
- reporting `RTSP: yes`, `RTSP_ALT: alternative` - correct config
- reporting load 2.57 and 25% free memory - **indistinguishable from the five
  cameras that were working**
- accepting RTSP connections and completing negotiation
- running an ffmpeg process at 39% average CPU in Frigate

Every check that was easy to run said the camera was healthy.

### The one check that found it

Probe what the stream actually declares:

```
cam2  codec_name=h264  width=1920  height=1088     <- healthy
cam4  codec_name=h264  width=0     height=0        <- wedged
```

The encoder had stopped emitting SPS headers. RTSP connects, the session opens,
data flows, and the decoder can never learn the frame geometry. Downstream that
appears as:

```
Could not find codec parameters for stream 0 (Video: h264, none): unspecified size
```

which reads like an ffmpeg tuning problem - the message even suggests raising
`analyzeduration` and `probesize`. It is not. No probe size recovers a header
that is never sent.

### Fix

No per-service restart endpoint exists on this firmware (`stop_rtsp.sh` and
`start_rtsp.sh` both 404). Reboot is the only lever:

```
curl "http://<cam>/cgi-bin/reboot.sh"
```

Back in ~90 seconds, `width=1920 height=1088`, recording resumed.

## Why neither was noticed

Both failures share one property: **the thing that was easy to measure kept
reporting success while the thing that mattered was dead.**

- Frigate's container was gone, but the Tailscale container beside it was up
  29 hours, and every config file on disk was correct.
- cam4 answered every HTTP request put to it, with healthy-looking numbers,
  while serving a video stream with no dimensions.

This is the same failure of verification that produced the earlier corrupted-
recording incident: checking that frames arrived rather than that recordings
played. Liveness of a component is not liveness of the function it provides.

## Health-check scripts added

Three scripts, all read-only, all safe to run any time:

| script | answers |
|---|---|
| `scripts/nvr-status.sh` | per-camera fps, detector ms, GPU use; prints `STATUS: ALL OK` or names the stalled cameras |
| `scripts/probe-rtsp.sh` | what each camera's RTSP **actually declares** - catches `width=0` |
| `scripts/verify-recordings.sh` | fully decodes the newest segment per camera; exit 1 if any is unplayable |

`verify-recordings.sh` deliberately uses `ffprobe -count_frames` and no output
muxer. An earlier version of it used `ffmpeg -f null -` and reported all six
cameras CORRUPT - that was the null muxer complaining about non-monotonic DTS
caused by `-use_wallclock_as_timestamps` on capture. A test that cries wolf on
healthy input is worse than no test, because the next real failure gets ignored.

## Still open

- **Nothing monitors any of this.** The scripts exist but run only when invoked
  by hand. A scheduled check that runs `nvr-status.sh` and, on failure, tests
  whether the GPU is the cause and issues `wsl --shutdown`, would have caught
  both faults within minutes instead of a day.
- `restart: unless-stopped` gives no protection against a failing prestart hook.
- 20 hours of recording lost on all six cameras; 41 hours on cam4.

## Fault 3: the WSL keepalive had been dead for a day (found the same evening)

Reported from a phone on the LAN:

```
https://home-nvr.<your-tailnet>.ts.net/   ERR_CONNECTION_ABORTED
```

Tailscale's own log named the client:

```
15:51:05 http: TLS handshake error from 100.64.0.12:55720: EOF
```

### What was actually happening

`docker.service` was being stopped and started roughly every 30-60 seconds.
It was not crashing - systemd was stopping it cleanly:

```
systemd[1]: Stopping docker.service ...
systemd[1]: docker.service: Deactivated successfully.
systemd[1]: docker.socket: Deactivated successfully.
systemd[1]: Starting docker.socket ...
systemd[1]: Started docker.service ...
```

The cause was one level up. The distro's own systemd was restarting:

```
systemd[1]: Reached target multi-user.target
systemd[1]: Startup finished in 7.330s
systemd-journald: File .../user-1000.journal corrupted or uncleanly shut down
```

WSL was terminating the **distro** whenever it went idle, taking systemd,
Docker, Frigate and Tailscale with it every time.

Note that `uptime -s` inside the distro is misleading here - it reported a
steady `18:29:36` throughout. WSL2 runs one utility VM shared by all distros,
and `/proc/uptime` reflects that VM's kernel, not the distro's init. The VM
kernel really had been up the whole time. The distro on top of it had not.
Use `systemctl show docker --property=ActiveEnterTimestamp --value`, or
systemd's own startup lines, to see distro restarts.

### Root cause

```
Task    : HomeNVR-WSL-Keepalive
Action  : wsl.exe -d Ubuntu -u root -e sleep infinity
Last run: 2026-08-28 13:40:49
Result  : 1
Next run: (none)
Triggers: MSFT_TaskBootTrigger only
```

`wsl --shutdown` kills the keepalive with exit code 1. `install-boot-task.ps1`
registered the task with **an AtStartup trigger only**, so once the action
died, nothing re-ran it until the next Windows reboot. It had been dead since
the previous afternoon. `RestartCount=999` / `RestartInterval=PT1M` were set
but did not bring it back.

So the boot task, which exists specifically to keep the NVR alive, had itself
been silently dead for over 24 hours.

### Fix

Immediate: `Start-ScheduledTask -TaskName HomeNVR-WSL-Keepalive`.

Durable: `scripts/harden-keepalive.ps1` (needs elevation) adds a 5-minute
repeating trigger next to the boot trigger. `MultipleInstances` is already
`IgnoreNew`, so a healthy keepalive is never double-started and the repeat
only does anything once the task has actually stopped.

### The methodology error

Every check that said the NVR was healthy was run with `wsl -d Ubuntu -- ...`.
**Each of those commands starts the distro.** So the act of measuring created
the healthy state being measured: distro starts, Docker starts, containers
start, Frigate answers, the check passes, everything is torn down again.

The 8-minute soak reported 7/8 ALL OK for exactly this reason - each poll was
booting the distro it was testing. One poll returned blank and was written off
as "a transient wsl call race". That blank poll was the actual signal, and it
was explained away.

A phone that had not been near the machine all evening found it in one try.

**Rule: a probe that can start the thing it is probing cannot measure that
thing's availability.** Verification must use a path that has no power to
repair the fault - here, `curl` from the Windows host and from a real client,
touching WSL zero times.

### Verification after the fix

Twelve polls over 6.5 minutes using **curl only** - no `wsl` command was run
for the duration, so nothing in the test could start what it was measuring:

```
19:01:43  ok  tailnet=200 lan=200   (1/12)
   ...      all twelve identical
19:07:28  ok  tailnet=200 lan=200   (12/12)
```

The decisive evidence is not the 200s, it is that the timestamps underneath
them never moved:

```
systemd userspace since   19:00:48      (= keepalive start, to the second)
docker active since       19:00:57
frigate  started          19:00:54
tailscale started         19:00:56
frigate  uptime           389s and climbing
```

Before the fix `docker active since` advanced every 30-60 seconds. Holding a
single value across the whole window is what proves the distro stayed up on
its own. A growing Frigate uptime is the cheapest ongoing signal that this has
not regressed - it had been resetting to single digits all evening.

All six cameras at ~5 fps, detector 8.85 ms, and every newest segment decodes
at full resolution.

### Reading the keepalive's task result

Once the 5-minute repeat trigger is in place, the task's `LastTaskResult` will
usually be `2147946720` (`0x800710E0`, "the operator or administrator has
refused the request"). **That is the healthy state.** It means a repeat trigger
fired, found the keepalive already running, and declined to start a second
instance - `MultipleInstances=IgnoreNew` working as intended.

| LastTaskResult | meaning | healthy? |
|---|---|---|
| `267009` (`0x41301`) | task is currently running | yes |
| `2147946720` (`0x800710E0`) | repeat trigger refused, instance already up | yes - expected every 5 min |
| `1` | the action exited; keepalive is dead | no - repeat should revive within 5 min |

The one to watch for is a **State of `Ready` together with result `1`**, which
is how this failure presented: the action had exited and, with only a boot
trigger, nothing was scheduled to bring it back.

Confirmed stable 38 minutes after the fix, with `docker active since` still
reading `19:00:57`.
