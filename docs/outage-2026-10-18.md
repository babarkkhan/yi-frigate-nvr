# Recovery on October 18, 2026

The owner reported that the cameras appeared down. An independent VPS check,
performed before invoking WSL, confirmed zero capture FPS and no fresh
recordings for all six configured cameras. Frigate and Tailscale nevertheless
reported healthy containers. Cam6 was unreachable and had previously been
intentionally unplugged; its current physical power state was not confirmed.

## Findings and recovery

1. **WSL GPU access was broken.** Windows could query the RTX 4080 SUPER with
   driver 617.42, while WSL, including root, reported `GPU access blocked by
   the operating system`. Kernel diagnostics included dxg failures. The device
   node still existed. The initiating event was not established: this is not
   proof of another driver update, despite a similar earlier incident.
2. After stopping the NVR containers, restarting WSL restored GPU access.
   The existing coordinated recovery helper recreated Frigate and Tailscale
   from their cached pinned images. The helper correctly reported failure
   because camera capture had not yet resumed.
3. **The five reachable camera RTSP services also needed recovery.** TCP ports
   were open and camera SSH worked, but RTSP requests were reset/closed without
   a response. A user-approved brief NordVPN disconnect did not resolve this;
   NordVPN was reconnected. Restarting only cam2's RTSP service restored its
   RTSP response, video/audio packets and Frigate frames. The same firmware
   service stop/start sequence initially recovered cam1, cam4, cam5 and cam3.
   Laundry later lost its RTSP listener again. Process inspection revealed
   that the firmware stop command leaves grabbers running, so start creates
   duplicates. Recovery was corrected to stop RTSP/watchdog, explicitly stop
   the video grabbers, then start the configured service. This cleanup was
   applied to all five reachable cameras. Duplicate grabbers were observed;
   their causal role in the laundry recurrence was not isolated. No full
   camera reboot or firmware update was performed. The relationship between
   these service failures and the GPU outage remains unproven.
4. **The NVR LAN address changed.** Speaker commands were rejected because
   their camera-side scripts still allowed only the old address. Each of the
   five reachable cameras' scripts was backed up, then its single allowed
   source address was changed to the address observed in authenticated
   `SSH_CONNECTION`. The restricted command and key checks remain in place;
   arbitrary commands still return 126. Cam6 was not changed.
5. **A stale relay session blocked reconnection during recovery.** Following
   the VPN test/reconnect, the home tunnel repeatedly reported remote port
   forwarding failure. On the VPS, an old `nvr-tunnel` SSH session still held
   ports 18971 and 18555. Terminating only that verified session allowed the
   home service to reconnect. The server had no application-level client
   keepalive interval configured.

The dedicated `Match User nvr-tunnel` SSH configuration now sets
`ClientAliveInterval 15` and `ClientAliveCountMax 3`. This lets sshd detect an
unresponsive transport and release its listeners rather than relying solely
on TCP keepalives. The previous file was backed up; `sshd -t` passed, effective
configuration confirmed the settings only for the tunnel account, and SSH was
reloaded. The home tunnel was reconnected under the new policy. Root's interval
remains unchanged at zero. A fresh blackhole/failure-injection test was not run.

## Validation and remaining work

All five reachable cameras resumed around 5 capture FPS with advancing recording
timestamps. A newly completed recording from each decoded without errors and
contained H.264 video and AAC audio. The original bitstream workaround remains
enabled. No Frigate image, camera firmware or recording arguments were changed.

Final process checks found one video grabber and one RTSP server per reachable
camera. The independent gateway check passed capture/freshness for cams1–5;
its overall result still fails for offline cam6. Restricted speaker readiness
checks passed on all five; password rejection and idle-lock checks also passed
on cams2–5. Headless WebRTC received video/audio and sent synthetic silence
through the speaker bridge on cam1 and, after cleanup, cam3 using the public
TCP relay. Cam3 also passed a direct-LAN test. Earlier cam3 relay tests failed
or disconnected; the later pass does not establish long-term stability or
prove which cleanup corrected the intermittent behavior. No physical spoken
test or phone latency measurement was performed. NordVPN was reconnected.

The recording table describes the initial long outage. Later short service
maintenance gaps and the laundry recurrence occurred during recovery and are
not included in that table.

Reserve the NVR's LAN address at the router: allowing a single source address
is intentional, and another DHCP address change will break speaker access again.
Do not automatically widen that restriction to the entire LAN.

Container HTTP health alone missed approximately 35 hours of recording loss.
The existing independent gateway checker can identify this failure, but the
checks in this recovery were manually invoked. This work does not establish
continuous monitoring or alert delivery. Those still require explicit deployment
and an acceptance test, using capture and recording freshness rather than only
container health. Camera service restarts should remain bounded; this incident
does not justify an uncontrolled whole-fleet restart loop.

Private credentials and camera footage are excluded from this report. Existing
unrelated working-tree and runtime database changes were preserved.
